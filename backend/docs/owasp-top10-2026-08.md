# Endurecimiento OWASP Top 10 — agosto 2026

Mapeo de las 8 categorías de OWASP Top 10 (2017) contra el estado real del código, con la evidencia y
la acción tomada en este pase. La lista de 2017 sigue siendo la más citada en el ámbito académico; al
final de este documento hay una nota de equivalencia con OWASP Top 10 2021 (la vigente) por si el
jurado pregunta por la nomenclatura actual.

## 1. SQL Injection

**Estado: ya cubierto, verificado con intentos reales.**

Toda consulta pasa por Prisma (parametrizado por diseño) o por `$queryRaw` con plantillas etiquetadas
(`` prisma.$queryRaw`...${valor}...` ``), que también parametrizan cada interpolación — nunca se
concatena texto SQL en ningún módulo. Verificado en vivo el mismo día de este pase (ver
`backend/docs/pruebas-rendimiento-seguridad-2026-08.md`, sección 2.3): un intento de inyección contra
`GET /reportes/movimientos-por-periodo` fue rechazado con 400 por el whitelist de Zod antes de llegar a
la capa SQL, y un intento contra `GET /productos?busqueda=` se trató como texto literal sin alterar
datos.

## 2. Broken Authentication

**Estado: cerrado en este pase (2FA opcional vía TOTP).**

Ya existían: JWT de 22 min + refresh token opaco con rotación y revocación real (`backend/src/lib/
refresh-token.ts`, `backend/src/modules/auth/AuthService.ts`), bcrypt costo 12, rate limiting de
login (10 intentos/15min), mensajes de error genéricos (no revelan si un email existe).

Nuevo: verificación en dos pasos (TOTP, compatible con Google Authenticator/Authy) opcional para
cualquier usuario, con códigos de recuperación de un solo uso:

- Schema: `Usuario.totpSecret`/`totpHabilitado`, modelo `CodigoRecuperacion2FA` (solo se persiste el
  hash SHA-256 de cada código, igual que `RefreshToken`).
- Backend: `POST /auth/2fa/configurar` (genera secreto + QR), `POST /auth/2fa/verificar` (confirma con
  un código real, activa 2FA, entrega 8 códigos de recuperación en texto plano una única vez),
  `POST /auth/2fa/desactivar` (exige contraseña). `POST /auth/login` exige el código cuando la cuenta
  lo tiene activado, antes de emitir cualquier token.
- Frontend: sección "Seguridad de la cuenta" (`/mi-cuenta`) para activar/desactivar, y un segundo paso
  en el login cuando la cuenta lo requiere.
- Test: `backend/tests/integration/2fa.test.ts`.

## 3. Sensitive Data Exposure

**Estado: reforzado; un riesgo residual documentado, no resuelto en este pase.**

- `passwordHash` y `totpSecret` nunca se devuelven al cliente (`UsuariosService.sinCamposSensibles`).
- CORS ahora exige el origen exacto del frontend (`FRONTEND_URL`) en vez de reflejar cualquier origen.
- CSP y HSTS explícitos (ver punto 6 y 7).
- `pino` ahora tiene `redact` configurado para headers de autorización y campos de contraseña/código,
  como red de seguridad (hoy no se logueaba el body de todas formas).
- **Riesgo residual, documentado y no resuelto aquí:** el JWT y el refresh token se guardan en
  `localStorage` del navegador (`frontend/src/auth/token-storage.ts`), lo que los expone a robo si
  algún día existiera una vulnerabilidad XSS. Mitigado hoy por la ausencia verificada de XSS (ver punto
  7) y el nuevo CSP. La corrección completa (cookies `httpOnly` + `SameSite=strict`) es un cambio de
  flujo mayor (entra en juego CSRF, cambia refresh/logout) que queda como recomendación futura.

## 4. XML External Entities (XXE)

**Estado: no aplica.**

No hay ningún parser de XML en el repositorio (ni `xml2js`, `fast-xml-parser`, `xmldom`, `libxmljs`, ni
`DOMParser`/`XMLParser` manual). La carga masiva de productos parsea el `.xlsx` en el **navegador**
(`exceljs` del lado del frontend) y solo envía JSON ya validado por Zod al backend — el backend nunca
toca el archivo binario original. `exceljs` en el backend solo se usa para **exportar** reportes, no
para leer archivos de terceros.

## 5. Broken Access Control

**Estado: reforzado (defensa en profundidad) + tests de aislamiento nuevos.**

Las lecturas por id ya escopaban por `empresaId` (`buscarPorId` en cada repositorio). Las escrituras
(`actualizar`/`softDelete`) dependían solo de que el service llamara a `obtener(id)` antes — una
convención, no una garantía a nivel de base de datos. Se agregó `empresaId` al `where` de `update()` en
Productos, Clientes, Proveedores, Categorías, Marcas, Unidades de Medida y Almacenes (Prisma soporta
filtros adicionales no-únicos junto al id en `update`/`delete` desde hace varias versiones): si algún
módulo nuevo se saltara el chequeo del service, Prisma rechaza el `update` completo (no encuentra la
fila) en vez de escribir sobre el registro de otra empresa.

Nuevo `backend/tests/integration/tenant-isolation.test.ts`: crea dos empresas, intenta leer/actualizar/
eliminar registros de la otra empresa por id — siempre `404`, nunca revela si el registro existe.

## 6. Security Misconfiguration

**Estado: cerrado en este pase (visor de errores para Super Admin).**

El manejador de errores (`ErrorHandlerMiddleware.ts`) ya **nunca** enviaba el stacktrace al cliente
(siempre un mensaje genérico), pero no existía ningún registro persistente y consultable de esas
excepciones — solo quedaban en la consola del proceso. Nuevo:

- Modelo `ErrorLog` (mensaje, ruta, método, código HTTP, categoría, stacktrace, usuario, empresa, ip,
  trace ID, fecha).
- El middleware persiste cada error 500 real de forma *fire-and-forget* (nunca retrasa ni rompe la
  respuesta que ya recibió el cliente).
- Nuevo módulo `backend/src/modules/errores`, endpoint `GET /errores` gateado
  `requireRole("SUPERUSUARIO")` — igual que `/admin` y `/auditoria`, un administrador común **no** ve
  este rastro técnico (así lo pidió explícitamente el usuario: "no les compete conocer del tema").
- Frontend: página `/errores` con buscador, rango de fechas y detalle con stacktrace, inspirada en el
  visor equivalente del sistema de referencia (SGA).
- Cabeceras: CSP y HSTS explícitos en vez de solo los defaults de Helmet (ver `app.ts`).

## 7. Cross-Site Scripting (XSS)

**Estado: ya bien protegido; reforzado con CSP explícito.**

Cero usos de `dangerouslySetInnerHTML` o `innerHTML =` en todo `frontend/src/` (confirmado por
búsqueda exhaustiva) — React escapa por defecto cualquier texto en JSX. Se agregó un CSP explícito
(`script-src 'self'`, `object-src 'none'`, `frame-ancestors 'none'`, etc.) como defensa adicional
demostrable, en vez de depender solo de los defaults de Helmet.

## 8. Insecure Deserialization

**Estado: no aplica.**

No hay `eval`, `new Function`, `vm.*`, ni librerías de deserialización insegura (`node-serialize`,
`serialize-javascript`) en el código de la aplicación. Todo el parseo de entrada pasa por esquemas Zod
explícitos; el único `JSON.parse` fuera de los internos generados de Prisma es sobre el propio body ya
parseado por `express.json()`.

## Dependencias (parte de "Using Components with Known Vulnerabilities")

Se fijaron versiones exactas (sin `^`) en ambos `package.json` — congela lo que hoy se sabe que
funciona y evita que una actualización automática instale una versión recién comprometida sin revisión
manual, que es el patrón real detrás de los ataques recientes a la cadena de suministro de npm (una
cuenta de mantenedor comprometida publica una versión maliciosa de un paquete ya instalado). Cambiar de
npm a pnpm **no** protege contra ese patrón específico — el problema está en el paquete, no en el
gestor — así que se descartó esa migración a favor de esta mitigación con evidencia real.

Hallazgo real corregido: `exceljs` (dependencia de producción en ambos paquetes) declara
`uuid: ^8.3.0`, versión con una vulnerabilidad conocida (`GHSA-w5hq-g745-h8pq`, falta de validación de
límites de buffer). No existe una versión más nueva de `exceljs` que actualice esa dependencia (4.4.0
es la última estable). Se usó el campo `overrides` de npm para forzar `uuid@^11.1.1` en todo el árbol
de dependencias sin tocar `exceljs`, y se verificó en vivo (exportar/leer un `.xlsx` de prueba) que
`exceljs` sigue funcionando con la versión forzada.

**Resultado final de `npm audit` en ambos paquetes: 0 vulnerabilidades.**

Node.js `v22.16.0` / npm `10.9.2`, ahora declarado explícitamente en `engines.node` de ambos
`package.json` (antes no estaba documentado en el repositorio).

## Nota: mapeo a OWASP Top 10 2021 (la versión vigente)

La lista usada en este documento es la de 2017. La versión 2021, vigente hoy, reorganiza y renombra
varias categorías:

| OWASP 2017 (usado aquí) | OWASP 2021 equivalente |
|---|---|
| A1: Injection (SQL Injection) | A03: Injection |
| A2: Broken Authentication | A07: Identification and Authentication Failures |
| A3: Sensitive Data Exposure | A02: Cryptographic Failures |
| A4: XML External Entities (XXE) | Absorbida dentro de A05: Security Misconfiguration |
| A5: Broken Access Control | A01: Broken Access Control (sigue primera en la lista) |
| A6: Security Misconfiguration | A05: Security Misconfiguration |
| A7: Cross-Site Scripting (XSS) | Absorbida dentro de A03: Injection |
| A8: Insecure Deserialization | Ampliada a A08: Software and Data Integrity Failures |
| — | A06: Vulnerable and Outdated Components (cubierto arriba, sección de Dependencias) |
| — | A09: Security Logging and Monitoring Failures (cubierto por el visor de Errores, punto 6) |
| — | A10: Server-Side Request Forgery (SSRF) — no aplica: la API no hace requests salientes a URLs provistas por el usuario |
